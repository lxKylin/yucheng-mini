## Context

现有健康能力已分为每日状态、指标追踪、药品和检查提醒等独立数据域；健康子包已承载“状态记录”和“指标追踪”二级页面。“我的”页的记录与复盘区域适合作为健康历程入口。实现动机和产品范围见 [proposal.md](proposal.md)，行为约束见 [health-timeline spec](specs/health-timeline/spec.md)。

## Goals / Non-Goals

**Goals:**

- 为关键健康事件建立独立、按用户隔离、可长期查询的数据域。
- 延续健康子包、Zustand、云端 service、二级页和 BottomSheet 的既有边界。
- 用日期精度和治疗时段表达不完整日期与持续治疗，避免伪造精确医疗事实。
- 在每次远端写入成功后再更新内存列表，令失败状态和已有数据保持一致。

**Non-Goals:**

- 不复用每日状态的“每日唯一”约束，也不将事件塞入指标、药品或检查提醒记录。
- 不在第一版自动从开药、检查完成或每日状态生成历程事件。
- 不实现附件、图片/报告上传、PDF 导出、医生共享、搜索、诊断推断或提醒联动。

## Decisions

### 独立事件模型与日期表达

新增 `HealthTimelineEvent` 与事件类型联合类型，建议覆盖：确诊或疑似诊断、症状或病程变化、检查结果、就诊复诊、治疗开始或调整、住院或手术、重要里程碑、其他。每项保存逻辑 `id`、`eventType`、`title`、`occurredAt`、`note`、关联药品/检查 ID、`createdAt`、`updatedAt`；治疗类额外保存可选 `endedAt` 和 `isOngoing`。

`occurredAt` 统一保存为可排序的 `YYYY-MM-DD`，录入和展示均精确到日。治疗结束日期也精确到日，且不得早于开始日期。

备选方案是把日期保存为多个可空字段或直接使用自由文本。前者增加查询和排序复杂度，后者无法可靠筛选；统一的完整日期字符串更符合现有日期模型。

### 独立云端集合和访问兼容

新增 `healthTimelineEvents` 集合、对应 service 和迁移工具。读取按当前用户的 `_openid` 与 `userId` 两种历史归属字段查询、去重后排序；写入将当前 `userId` 写入记录。创建、更新、删除都在当前用户身份范围内进行，远端操作成功前不改变本地成功态。

部署说明补充 `_openid + occurredAt`、`userId + occurredAt` 的索引，以支持按用户倒序读取和日期范围查询。首版按固定页大小增量加载，列表滚动到底部后继续读取下一页；筛选基于已加载事件，若仍有下一页则提供继续加载入口，避免以固定上限截断长期档案。

复用每日状态集合会导致每日唯一和长期事件多条记录的规则冲突；复用指标记录则会混入数值和参考范围语义，均不采用。

### 只读关联而非业务联动

事件仅保存 `relatedMedicineIds` 与 `relatedCheckupIds`。表单从当前可用药品和检查提醒中选择，展示时用当前数据解析名称；关联对象不存在时以“关联项目已不可用”呈现。历程域不订阅或修改提醒任务，也不写回任何药品、检查、每日状态或指标数据。

备选方案是把每一次开药或检查完成自动投影为事件。虽然减少录入，但会产生噪声、重复记录和删除同步问题，且会模糊“用户确认的医疗历程”与“系统任务历史”，因此留作后续独立设计。

### 二级页与表单交互

在“我的”页的现有记录与复盘菜单中加入健康历程入口，并在健康子包注册新页面，不增加 Tab 或修改中央新增入口。页面包含标题/说明、年份与类型筛选、事件时间轴、分页加载状态和新建入口。

新建/编辑使用既有 BottomSheet 交互：基础字段为类型、标题、发生日期和可选备注；仅治疗类展开结束日期与进行中状态；关联选择保持可选。标题去除首尾空格后必填并设定长度上限，备注设定长度上限，发生日期不得晚于当天。删除始终经确认弹窗。

在一个页面内内嵌编辑表单的备选方案会使时间轴、选择控件和校验状态耦合；BottomSheet 与现有健康录入体验一致，且更利于保持页面文件规模受控。

### 状态管理与视图派生

新增独立 Zustand store，维护事件列表、初次加载状态、追加加载状态、是否还有更多、加载错误、提交状态及 create/update/delete/retry/load-more 动作。hook 使用 `useSyncExternalStore` 订阅，并用纯函数派生年份选项、筛选结果和稳定排序结果。

初次加载中只显示加载态；加载失败显示错误态和重试；真实空数据才显示空态。提交期间禁用重复提交和关闭表单操作；失败时不清空表单。该状态模型参考指标追踪，但不与其 store 共享，防止不同生命周期互相干扰。

## Risks / Trade-offs

- [Risk] 长期事件数量增加导致首屏或云端读取慢 → Mitigation: 按时间倒序分页，加载更多时保留已读取时间轴。
- [Risk] 事件类型或关联字段过多造成首次录入负担 → Mitigation: 仅类型、标题和日期必填，备注、治疗结束信息和关联均可选，治疗字段按类型条件展示。
- [Risk] 健康信息属于敏感个人数据 → Mitigation: 使用现有当前用户身份边界、只读写本人数据，不提供共享或导出入口，并避免医疗判断文案。
- [Risk] 关联对象被删除后名称无法解析 → Mitigation: 保留关联 ID 和事件本身，以不可用提示替代静默丢失。

## Migration Plan

1. 先部署 `healthTimelineEvents` 集合与用户/发生日期复合索引说明，再发布客户端读取和写入功能。
2. 新能力只新增数据域和“我的”页二级入口，不迁移或改写任何既有药品、检查、每日状态和指标记录。
3. 上线后以空态引导用户手动创建首条事件；不回填历史提醒或状态数据。
4. 回滚时移除入口、路由和新域调用即可；独立集合中的用户数据保持不影响现有提醒业务。
