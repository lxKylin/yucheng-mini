## Context

指标追踪当前已经具备指标类型新增/编辑、指标记录保存、趋势图和最近记录展示。现有类型 `HealthMetricStatus` 已包含 `active | hidden | deleted`，服务层拉取指标类型时也会过滤 `deleted`，但页面和 store 尚未暴露停止追踪/删除动作。

指标列表当前主要依赖指标类型更新时间排序。用户编辑单位或参考范围后，指标可能被推到前面；这不一定代表用户最近关注该指标。考虑到血常规、生化指标可能很多，本次只补轻量管理闭环，不引入用户手动维护分类系统。

## Goals / Non-Goals

**Goals:**

- 允许用户从编辑指标流程中停止追踪/删除当前指标。
- 删除采用软删除：指标类型标记为 `deleted`，历史指标记录保留。
- 删除后当前页面立即移除该指标，并选择下一个可展示指标或进入空态。
- 指标切换列表按“最近记录优先，其次指标更新时间”展示。
- 保持 loading、empty、error、submitting 状态可理解，失败时不丢失用户上下文。

**Non-Goals:**

- 不新增指标分类字段、分类 Tab 或分类管理表单。
- 不实现拖拽排序、置顶、收藏或用户自定义顺序。
- 不物理删除 `healthMetricRecords` 历史记录。
- 不因为指标异常新增提醒、订阅消息或诊断建议。

## Decisions

1. **使用软删除而不是物理删除**

   - 做法：新增服务/store 动作，将 `healthMetricTypes` 对应文档的 `status` 更新为 `deleted`，同步更新 `updatedAt`。
   - 理由：健康数据误删成本高；现有类型与服务过滤已为 `deleted` 预留路径。
   - 备选：级联删除指标记录。放弃原因是不可恢复且会破坏历史复盘材料。

2. **删除入口放在编辑指标 BottomSheet 内**

   - 做法：编辑已有指标时，在保存按钮之外展示低强调的“停止追踪/删除指标”操作；新增指标模式不展示。
   - 理由：用户删除的是一个已存在的指标类型，和编辑名称、单位、参考范围属于同一管理语境。
   - 备选：在横向指标 tab 上直接放删除。放弃原因是容易误触，也会让切换区变重。

3. **已有记录的指标删除前必须二次确认**

   - 做法：确认文案说明“删除后不再展示该指标趋势和记录，历史数据保留”；无记录指标也仍需确认，但文案可以更短。
   - 理由：删除改变页面可见数据，需要明确影响；同时避免用户误以为历史记录会被物理清空。

4. **排序在前端派生，不新增排序字段**

   - 做法：在 hook 或工具函数中根据每个指标的最新记录日期/更新时间生成 summaries 顺序；没有记录的指标按 `updatedAt` 排序。
   - 理由：本次目标是轻量可达性改善，不需要迁移数据或维护排序持久化。
   - 备选：新增 `sortOrder` 字段或拖拽排序。放弃原因是会引入排序持久化、冲突处理和额外管理负担。

## Risks / Trade-offs

- 删除请求成功但记录缓存仍存在 -> store 删除指标类型时同步清理该指标的页面选中态，记录缓存可保留在内存但不得被当前 UI 引用。
- 云端更新失败 -> 保持 BottomSheet 打开或保留当前页面上下文，展示失败提示，允许用户重试。
- 只按已加载记录排序可能不完整 -> 首屏至少依据已加载记录和指标更新时间稳定排序；不为排序额外批量拉取所有指标记录，避免放大请求成本。
- “删除”文案可能让用户误解为永久清除 -> UI 文案使用“停止追踪/删除指标”，确认说明历史记录保留且不再展示。
