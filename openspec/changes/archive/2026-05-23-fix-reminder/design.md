## Context

小程序当前在个人页提供一个统一的微信提醒授权入口，用户侧理解为“开启微信提醒”。代码中已经存在三类订阅消息发送场景：开药日程提醒、药品过期提醒、检查/复诊提醒；对应模板 ID 已集中配置在常量中。

现有 `requestWechatReminderSubscription()` 仍按单模板逻辑实现，只读取一个环境变量模板 ID，并只向 `Taro.requestSubscribeMessage` 传入一个 `tmplIds`。这导致另外两类模板没有进入授权流程。与此同时，云函数仍通过用户表中的单一 `wechatSubscriptionStatus` 判断是否有可用订阅资格。

## Goals / Non-Goals

**Goals:**

- 个人页一次订阅请求覆盖全部三类提醒模板。
- 保持一个用户可理解的统一微信提醒授权入口。
- 保持现有用户级订阅资格字段和云函数发送模型不变。
- 对多个模板的授权结果进行清晰归并，避免数组模板被当作单个字符串读取。
- 只有全部模板授权成功时，个人页才显示消息订阅已开启。
- 为未授权模板或配置异常模板保留诊断信息，避免吞掉 `reject`、`ban` 和 `filter` 结果。

**Non-Goals:**

- 不新增三套提醒订阅开关。
- 不把用户级订阅资格拆成开药、过期、检查三个字段。
- 不修改 `reminder`、`expiryReminder`、`checkupReminder` 云函数的发送和消费逻辑。
- 不改动数据库结构或历史用户数据。

## Decisions

### 继续使用统一授权入口

采用一个“开启微信提醒”入口来请求三类模板，而不是让用户分别开启三种提醒订阅。

原因：当前产品的信息架构仍是统一微信提醒授权，三套开关会增加重复 UI 和解释成本。轻量修法能先修复“只有一个模板进入授权流程”的真实缺陷。

替代方案：为三类提醒分别提供开关和状态。该方案语义更精确，但会牵动用户表结构、个人页展示、云函数消费逻辑和用户理解成本，本次不采用。

### 使用常量数组作为前端订阅源

前端订阅服务从 `WECHAT_REMINDER_TEMPLATE_ID` 获取模板 ID 列表，并将有效 ID 数组传给 `Taro.requestSubscribeMessage`。

原因：三类模板已经在常量中集中维护，服务层不应再读取单个 `ENV_TEMPLATE_ID` 造成配置分裂。

替代方案：继续通过环境变量拼接模板 ID。该方案会让小程序端模板配置来源不透明，且与当前常量配置不一致，本次不采用。

### 以“全部模板 accept”归并为可用授权

订阅结果按模板 ID 逐个读取，只有三类模板全部返回 `accept`，服务层返回 `enabled: true`，个人页继续把用户级状态更新为 `available`。

原因：个人页只有一个统一的“消息订阅已开启”状态，这个状态需要代表三类提醒都已获得授权，否则用户会误以为所有提醒都能发送微信消息。

替代方案：任一模板 `accept` 就算开启成功。该方案更宽松，但会让页面状态和真实授权覆盖范围不一致，本次不采用。

### 任意模板失败都阻断页面开启状态

当任意模板返回 `reject`、`ban`、`filter` 或未知结果时，服务层返回 `enabled: false`，个人页不得把用户级状态更新为 `available`，并通过 message 告知存在未开启或配置异常的模板。调试日志可记录每个模板的具体结果。

原因：微信订阅消息授权是按模板返回结果，但页面只展示一个统一开启状态；为了让页面状态可信，任何模板失败都应阻止统一开启状态。

## Risks / Trade-offs

- 全部模板 `accept` 才显示开启，用户可能因为单个模板失败而无法开启统一状态 → 通过提示说明哪类模板未开启或配置异常，引导重新授权或检查后台模板。
- 粗粒度订阅状态仍无法记录三类模板的独立生命周期 → 本次保留统一状态模型，后续如需要分别续订或分别展示再升级为分模板状态。
- 微信设置页可能无法直接按模板细粒度恢复所有授权 → 保持打开设置入口，并允许用户重新点击统一授权入口重试。
- 常量数组中出现空字符串或重复 ID → 服务层应过滤空值并去重，避免请求无效模板。
