## 背景

当前小程序以统一的 `Medicine` 实体为中心。开药提醒作为 `Medicine` 上的一组字段存在，并通过首页、提醒列表、药箱和我的页面展示。现有底部 Tab 为「首页 / 提醒 / 药箱 / 我的」。

复诊和检查事项与开药周期不同。一次检查可以和某个药品相关，也可以独立存在，例如化验、影像检查、专科复诊或定期指标复查。如果把检查继续塞进 `Medicine` 字段里，药品模型会承担过多与预约、检查完成、历史记录和订阅消息有关的逻辑，后续筛选和维护都会变复杂。

## 目标 / 非目标

**目标：**

- 新增独立的「检查」底部 Tab，用于管理复诊和检查提醒。
- 将检查提醒建模为独立于开药提醒的业务域。
- 支持完整用户闭环：创建检查提醒、查看紧急程度、查看详情、暂停/恢复、完成，并可选择设置下一次检查。
- 首页风险/待办区域展示紧急检查提醒，与开药提醒形成统一的今日待办视角。
- 检查提醒保存到云端，并通过定时云逻辑发送微信订阅提醒。
- 保持现有 `Medicine` 和开药提醒行为不变。

**非目标：**

- 不做报告 OCR、报告上传、趋势图或结构化检查结果解读。
- 不把检查提醒合并进现有 `medicines` 集合。
- 不要求每个检查提醒必须绑定药品。
- 不大规模重设计首页、提醒列表、药箱和我的页面，只做必要集成。
- 不改变当前开药提醒订阅模板语义；如检查提醒需要不同模板，应单独配置。

## 设计决策

### 决策 1：使用独立的检查业务域

新增 `CheckupReminder` 和 `DerivedCheckupReminder` 类型、新的检查服务层、新的检查 store/hooks，并将持久化记录存入独立的 `checkups` 集合。

原因：检查提醒有自己的标题、类型、检查日期、完成状态、医院、可选药品关联和历史记录。独立业务域能保持现有 `Medicine` 兼容边界稳定，也方便未来扩展检查相关功能而不影响开药提醒。

备选方案：在 `Medicine` 上增加检查字段。该方案不采用，因为一个药品可能对应多个检查事项，而且很多检查事项并不依附于药品。

### 决策 2：检查提醒以 Tab 为主，首页只展示紧急摘要

新的「检查」Tab 负责检查提醒的列表、筛选、创建/编辑和详情流程。首页只消费检查 store 的派生摘要，将逾期和今日到期的检查提醒纳入风险/待办区域。

原因：用户需要一个专门空间管理复诊检查，但紧急医疗任务也应该出现在第一屏。

备选方案：只在首页展示检查提醒。该方案不采用，因为首页空间不足以承载筛选、历史和详情管理。

### 决策 3：V1 使用简单日期提醒，不做复杂周期规则

每条检查提醒包含 `targetDate`、`remindAdvanceDays` 和 `remindTime`。完成时记录完成日期，并允许用户手动填写下一次检查日期。

原因：这能覆盖真实的复诊提醒需求，同时避免引入复杂周期规则。复诊周期常常由医生当次决定，手动设置下一次日期更贴近实际。

备选方案：支持每 N 个月等周期规则。该方案暂缓，因为会增加表单和派生逻辑复杂度。

### 决策 4：检查提醒的云端扫描与开药扫描分离

优先新增独立定时云函数，例如 `checkupReminder`；如果复用现有云函数，也必须在代码中形成清晰分支。检查提醒的查询条件、消息文案、去重字段必须保持独立。

原因：现有云函数默认读取开药相关字段并计算下次开药日期。检查提醒需要不同字段和消息语义，不能直接复用开药计算逻辑。

备选方案：直接复用现有开药扫描逻辑。该方案不采用，因为会把检查提醒错误地耦合到 `Medicine` 的开药周期计算。

### 决策 5：药品关联使用可选 ID 列表

检查提醒可保存 `relatedMedicineIds: string[]`，但空列表也是合法状态。检查 Tab 可以在有药品数据时显示关联药品名称。

原因：部分检查与药品相关，例如用药后的肝功能复查；另一些检查则与科室、疾病或体检有关。

备选方案：强制每条检查提醒关联一个药品。该方案不采用，因为会阻碍年度体检、专科复诊等常见场景。

## 风险 / 权衡

- 新增 Tab 会让底部导航从 4 项变为 5 项 -> 使用短标签和清晰图标，并在小屏上验证文字可读性。
- 独立 store/service 会重复一部分提醒机制 -> 可复用小型日期工具和状态常量，但保持领域 payload 明确。
- 微信订阅模板字段可能不适合检查提醒文案 -> 将模板作为配置项，缺少必要环境变量时在云函数日志中明确报错。
- 首页集成可能让信息变拥挤 -> 只展示合并后的紧急数量和简短任务列表，不复制检查 Tab 的完整内容。
- 新 `checkups` 集合可能出现云数据库索引告警 -> 明确用户、状态、检查日期、最近发送日期等查询字段，并补充相应索引。

## 迁移计划

1. 新增检查类型、常量、日期派生函数、服务层和 store，不改变现有药品代码路径。
2. 新增「检查」Tab 路由和图标资源，再实现检查页面与组件。
3. 在用户登录后的应用启动流程中加载检查提醒。
4. 通过派生 selector 接入首页摘要，确保现有开药提醒渲染不受影响。
5. 新增 `checkups` 定时云提醒逻辑，并尽量与当前开药提醒云函数分开部署。
6. 回滚时移除「检查」Tab 路由并禁用检查云触发器；现有 `medicines` 数据不受影响。
