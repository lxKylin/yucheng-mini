## 背景

当前小程序已经形成「首页 / 提醒 / 药箱 / 检查 / 我的」底部导航。开药提醒由提醒列表完整管理，检查提醒由检查 Tab 完整管理，首页承担风险概览和近期待办露出。

现状的问题在于首页的内容组织仍以开药提醒为主：`最近提醒` 固定展示最近 3 条开药提醒，而紧急检查提醒仅在有条件时追加到其下方。用户在首页第一屏看到的是开药列表，检查提醒即使逾期也可能被滚动位置遮挡。与此同时，检查 Tab 顶部有较重的独立 Hero，而提醒 Tab 没有对应结构，视觉和信息层级上显得割裂。

本设计保留检查提醒的独立数据域和独立 Tab，只调整首页聚合视角与检查 Tab 的页面层级。

## 目标 / 非目标

**目标：**

- 首页成为跨开药提醒和检查提醒的统一风险中心。
- 首页优先展示最紧急的待办事项，而不是按业务类型分区后再展示。
- 检查提醒在首页有稳定、可理解的类型标识，并能跳转到完整检查管理。
- 检查 Tab 与提醒 Tab 在页面结构上更一致，减少「单独追加模块」的感受。
- 保持现有开药提醒、检查提醒的数据模型和云端能力不变。

**非目标：**

- 不合并 `Medicine` 与 `CheckupReminder` 数据模型。
- 不把检查提醒完整管理能力搬到首页。
- 不重做药箱、我的页面。
- 不新增订阅消息模板、云函数或后端集合。
- 不改变开药提醒和检查提醒的完成语义。

## 设计决策

### 决策 1：首页使用统一优先待办池

首页将开药提醒与检查提醒转换为统一的首页待办视图模型，再按风险排序展示。视图模型至少包含：`id`、`type`、标题、状态文案、目标日期、提醒时间、风险等级、跳转目标和主要操作。

排序优先级为：

1. 已逾期事项。
2. 今日到期事项。
3. 7 天内或提醒窗口内事项。
4. 更远的有效事项。
5. 同一风险等级内按目标日期从近到远排序。

备选方案是保留「最近提醒」与「紧急检查」两个分区。该方案不采用，因为它会让开药提醒天然占据首页上方位置，无法保证检查风险与开药风险同权露出。

### 决策 2：首页展示标题从「最近提醒」改为「优先待办」

首页模块语义应从时间最近改为风险优先。文案建议使用「优先待办」，副文案使用「按逾期、今日和临近事项排序」。

当统一待办为空时，首页展示稳定空状态和新增入口；当检查没有紧急项时，不展示虚假检查卡片，但仍保留进入检查 Tab 的路径。

### 决策 3：首页待办卡片明确业务类型

首页中的每条待办必须标识来源类型，例如「开药」或「检查」。类型标识可以是轻量标签，也可以是卡片上的固定字段。这样首页可以使用统一列表，但用户仍能快速理解后续操作差异。

开药卡片的主操作仍是「已开药」和「查看详情」。检查卡片的主操作仍是「完成」和「查看详情」。若共用卡片抽象，应只抽象首页展示层，不改变各自业务 action。

### 决策 4：检查 Tab 弱化独立 Hero，回到列表工作台结构

检查 Tab 应与提醒 Tab 更接近：搜索、状态筛选、类型筛选、列表内容、右下角新增。现有大 Hero 中的统计信息可以下沉为轻量统计条，或直接由筛选项数量承载。

备选方案是在提醒 Tab 也新增类似 Hero。该方案不优先采用，因为提醒 Tab 当前已经是清晰的管理列表，增加 Hero 会占用首屏效率。

### 决策 5：派生逻辑优先放在 hooks 或 utils 层

首页不应在 JSX 中散落跨域排序规则。建议新增或调整一个首页派生函数，例如 `useHomeRiskFeed`，内部消费 `useDerivedList()` 和检查提醒派生数据，输出统一待办列表和统计数据。

这样可以让首页渲染保持简单，也方便后续测试排序、数量截断和排除暂停/完成/删除记录等规则。

## 风险 / 权衡

- 首页待办模型过度抽象 → 仅抽象首页展示所需字段，不反向影响药品和检查数据模型。
- 统一列表导致操作差异变隐蔽 → 每条卡片必须带类型标识，并保留对应业务的主操作文案。
- 检查 Tab 去掉大 Hero 后信息变弱 → 保留筛选计数或轻量统计，让用户仍能看见紧急数量。
- 首页排序变更可能影响用户对「最近 3 条」的预期 → 文案改为「优先待办」，避免继续暗示按最近开药提醒展示。
- 旧的检查首页摘要变量可能残留 → 实现时需要执行 TypeScript 检查，重点覆盖 `src/pages/home/index.tsx` 的旧统计变量引用。
