## Context

当前 `Medicine` 实体同时承载药品资料、服药信息和开药提醒配置。`dosagePerUse` 与 `timesPerDay` 已能表达规则的每日计划，但系统没有库存基准、实际服药流水或剂量生效历史。“本次已开药”只更新开药日期与最近五次开药历史，每日健康状态也只记录整天的总体用药情况，无法确定某一种药实际消耗了多少。

因此，本次不能把余量描述为精确库存，也不能依赖粗粒度健康状态自动扣减。核心目标是在不引入逐次服药打卡和每日持久化任务的前提下，为用户提供一个透明、可随时校准的计划估算。

产品文档此前明确约束药箱不展示剩余量。本次是对该边界的有意调整：只有用户主动开启余量跟踪并录入真实基准时才展示估算，未开启的存量药品继续维持当前行为。

## Goals / Non-Goals

**Goals:**

- 让片剂用户能稳定录入 `0.25`、`0.5` 等小数剂量，并以 `1/4 片`、`1/2 片`等易读文案展示。
- 允许用户选择性录入某个日期盘点后的实际总量，并按规则用药计划动态估算今天剩余多少、约可使用几天。
- 让用户在开药、盘点或发现估算偏差时快速重设当前总量。
- 剂量调整后只影响生效日之后的估算，不用新剂量反向重算旧周期。
- 对按医嘱、每日次数为 0、待盘点等无法可靠估算的状态退化为手动维护。
- 保持药箱默认顺序稳定，并通过明确筛选帮助用户在就医前找到余量不足药品。
- 为新增、编辑、更新库存和记录开药提供完整校验、提交态和失败反馈。

**Non-Goals:**

- 不实现逐次服药提醒、服药打卡或漏服自动修正。
- 不实现盒、板、片之间的包装换算；第一版库存单位必须与每次用量单位一致。
- 不实现药品批次、不同有效期、先进先出或多地点库存。
- 不使用每日健康状态推断具体药品消耗。
- 不新增库存不足微信订阅消息或后台每日落库扣减任务。
- 不以库存估算替换现有固定开药周期与开药提醒。
- 不提供家属共享编辑、多人并发盘点或审计历史页面。

## Decisions

### 使用库存基准快照，而不是每日写入扣减记录

在 `Medicine` 中增加以下持久化字段，命名可在实现时按现有风格微调，但语义必须保持：

- `inventoryTrackingEnabled: boolean`：是否跟踪余量，存量数据默认 `false`。
- `inventoryEstimateMode: 'automatic' | 'manual'`：自动按计划估算或仅手动维护。
- `inventoryBaseQuantity: number`：盘点基准数量，允许为 0，最多两位小数。
- `inventoryBaseDate: string`：基准日期，表示“截至该日期盘点后的实际剩余量”。
- `inventoryNeedsCalibration: boolean`：开药后未填写总量等情况下标记为待盘点。
- `inventoryUpdatedAt: string`：最近一次人工盘点或系统结算时间。

派生层增加预计剩余数量、预计可用天数和库存状态，不把每天计算结果写回云数据库。这样打开应用时即可得到当前估算，避免定时任务重复扣减、漏跑和时区幂等问题。

备选方案是每天由云函数将库存减去计划用量。该方案仍然不知道用户是否实际服药，同时带来重复执行和漏执行风险，因此不采用。

### 余量计算采用透明的日级口径

自动估算满足以下前提：余量跟踪开启、模式为 `automatic`、不处于待盘点状态、每次用量大于 0、每日次数大于 0，且用药时机不是“按医嘱”。

计算口径：

```text
每日计划用量 = 每次用量 × 每日次数
经过天数 = max(0, 今天与基准日期之间的自然日差)
预计剩余量 = max(0, 基准数量 - 每日计划用量 × 经过天数)
预计可用天数 = floor(预计剩余量 ÷ 每日计划用量)
```

基准日期当天不再自动扣减，计算从下一个自然日开始。数量计算统一四舍五入到两位小数，展示时去掉无意义的末尾零，防止 JavaScript 浮点误差产生 `0.499999` 等文案。

该口径不尝试判断今天已服了几次，UI 必须使用“预计剩余”“按当前剂量估算”等文案。用户对准确性有疑问时，以重新盘点输入为准。

### 小数剂量使用字符串编辑态，提交时再规范化

`MedicineComposer` 的每次用量输入在编辑过程中保留字符串，避免输入 `0.` 时被立即转换为 0 并清空。提交时再校验为大于 0、最多两位小数的数字。

片剂展示 `1/4 片`、`1/2 片`、`1 片`、`1.5 片`、`2 片`快捷值和自定义入口；其他剂型继续使用数字输入，避免暗示胶囊、注射剂等可以任意拆分。数据仍统一保存为数值，不新增“半片”或“四分之一片”单位。

### 余量跟踪独立于开药提醒和提醒暂停状态

药品可以不开启开药提醒但仍需要管理余量；暂停开药提醒也不等于暂停服药。因此 `reminderEnabled` 和 `Medicine.status` 不得控制余量扣减。

用户需要停止自动估算时，应显式切换为手动维护。重新启用自动估算前需要确认当前实际总量和基准日期，避免把暂停期间错误计入消耗。

当 `timesPerDay=0` 或 `scheduleTiming='按医嘱'` 时，系统自动使用手动模式，并解释“用量不固定，需手动更新余量”。

### 剂量调整时先结算旧计划，再启用新计划

当已开启自动估算的药品修改 `dosagePerUse` 或 `timesPerDay` 时，表单增加“新剂量生效日期”，默认今天，可选择不早于当前库存基准且不晚于今天的日期。

保存时先按旧计划计算到生效日期的预计剩余量，再将其写为新的 `inventoryBaseQuantity` 和 `inventoryBaseDate`，最后保存新剂量。之后的派生只使用新计划，不反向改变历史消耗。

如果用户修改用量单位，旧库存数量无法与新单位直接换算，系统必须要求重新填写当前实际总量；不能静默沿用旧基准。

### 开药后优先录入当前总量，而不是仅录入新增数量

所有“本次已开药”入口复用统一 BottomSheet。未开启余量跟踪时，流程仍只记录实际开药日期；已开启时额外提供“开药后的当前总量”，说明需要包含旧药余量和本次新开药品。

填写总量后，以实际开药日期作为新基准日期，清除待盘点状态。用户可以选择“稍后盘点”，此时仍记录开药日期，但将 `inventoryNeedsCalibration` 设为 `true`，药箱展示“已开药，待盘点”，不得继续展示旧的预计剩余量。

选择当前总量而不是“本次新增数量”，可以让每次开药同时消除此前漏服、剂量变化或人工误差，避免估算偏差长期累积。

### 药箱展示余量，但不自动改变默认顺序

已开启跟踪的药品卡片展示以下状态之一：

- `预计剩余 18.5 片 · 约可用 12 天`，并标注按计划估算。
- `当前记录 18.5 片 · 手动维护`，用于不规则用药。
- `已开药，待重新盘点`，用于基准已失效场景。
- `余量已用尽` 或 `余量不足`，用于明确风险。

药箱增加“余量不足”筛选，第一版使用固定 7 天阈值，仅包含自动估算中预计可用天数小于等于 7 天或预计剩余量为 0 的药品。默认“全部”列表沿用现有稳定顺序，不因每天的估算变化自动重排。本次不增加用户自定义阈值设置。

### 云端更新与页面状态保持现有单文档链路

库存基准、剂量和开药日期属于同一药品当前状态，通过现有 `medicines` 文档一次更新提交，避免本地先更新成功而云端部分字段失败。服务失败时 store 不得提前修改可见状态，BottomSheet 保留用户输入并展示可重试错误。

存量数据在迁移函数中补齐安全默认值：关闭余量跟踪、手动模式、基准数量 0、空基准日期、非待盘点。未开启跟踪时这些默认值不得出现在 UI 中。

## Risks / Trade-offs

- **用户把估算当作真实库存**：所有展示使用“预计”“按计划估算”，并提供显式盘点校准入口。
- **漏服、临时加量造成偏差**：第一版不追求逐次准确；开药后总量和随时盘点用于消除累计误差。
- **同一天内已服次数不明确**：采用日级口径，基准日不扣减；不展示小时级精度。
- **剂量变更与库存更新同时保存失败**：使用同一文档单次更新，失败时不改变本地状态并保留表单上下文。
- **不规则用药无法自动估算**：自动退化为手动维护，不输出虚假的可用天数。
- **库存单位变化导致不可比**：要求用户重新盘点，不做隐式单位换算。
- **字段增加影响存量数据**：迁移函数提供关闭跟踪的默认值，现有药品和提醒链路保持兼容。

## Migration Plan

1. 先增加类型、迁移默认值和纯函数派生验证，保证旧数据加载后默认关闭余量跟踪。
2. 接入药品新增/编辑表单、小数剂量和库存基准校验，再接入药箱展示与筛选。
3. 将首页、提醒列表、提醒详情的“已开药”入口统一到支持库存校准的流程。
4. 更新产品设计和开发计划中旧的库存边界，并完成存量数据、失败态和跨入口回归验证。

本变更不要求批量迁移云端文档；旧文档在读取时使用默认值，用户首次开启余量跟踪并保存后再写入新字段。
