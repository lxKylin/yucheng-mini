## Context

`expiryReminder` 当前由 `config.json` 配置为每周三 09:00 执行。函数以东八区当天计算唯一的 `targetExpiryDate`，数据库只查询该日期的活动药品，随后又以服务器本地时间对药品提醒时刻做 ±30 分钟判断。调度星期、日期候选和时间窗口彼此不匹配，因此部分记录没有任何一次执行机会。

本变更只修复药品过期提醒链路。现有集合仍使用 `medicines`，提前天数仍读取 `ENV_EXPIRY_ADVANCE_DAYS`，发送成功后仍通过 `lastWechatExpiryReminderDate` 防重。当前固定上限 1000、发送并发竞争、失败语义、敏感日志和三个云函数的公共时区实现已有独立审查任务，本次不合并处理。

## Goals / Non-Goals

**Goals:**

- 让任意星期到期的活动药品每天都有扫描机会。
- 让任意合法 `HH:mm` 提醒时刻都能命中至少一个调度窗口。
- 用单一纯函数确定到期日期、提醒时间窗口、跨午夜归属日期及未命中原因。
- 保持成功发送按计划提醒日期最多一次，并让日期不命中、时间不命中可分别统计。
- 通过不依赖云数据库和微信 API 的测试覆盖关键日期与时间边界。

**Non-Goals:**

- 不处理超过 1000 条活动药品的游标分页。
- 不新增事务 claim 或改变并发发送模型。
- 不统一改造 `reminder`、`checkupReminder` 的时间工具。
- 不改变订阅模板授权、用户资格消费或数据库字段结构。
- 不在本次任务中完成日志脱敏与平台失败重试语义改造。

## Decisions

### 触发器每 30 分钟执行一次

将定时器从每周一次改为全天每 30 分钟执行一次，与现有 ±30 分钟时间窗口配套。这样任何分钟精度的合法提醒时刻都至少会落入一个执行窗口，同时不需要为每条药品动态创建触发器。

替代方案是每天固定 09:00 扫描并忽略用户时刻，但会改变既有用户配置语义；另一个方案是每分钟执行，覆盖更精确但会带来不必要的调用与扫描成本，本次不采用。

### 先扫描活动药品，再由纯函数统一判定

数据库查询仅保留 `status: 'active'`，每条记录交给 `isExpiryReminderDue({ now, expiryDate, advanceDays, remindTime })`。函数返回 `{ due, reason, reminderDate }`：`reason` 为 `date_mismatch`、`time_mismatch`、`invalid_input` 或 `due`，调用方据此累计统计，不再在查询层和循环层分别实现日期规则。

替代方案是继续在数据库查询中限定 `expiryDate`。该方案读取更少，但日期未命中记录根本不会进入函数，无法形成统一判断和原因统计；规模问题由后续分页任务解决。

### 使用东八区计划发生时刻处理跨午夜窗口

纯函数把 `now` 映射为东八区时间，并在目标提醒时刻的前一天、当天、后一天三个候选发生时刻中选择与 `now` 最近者。只有最近差值不超过 30 分钟才视为时间命中；日期条件使用该计划发生时刻的东八区日期，而不是直接使用执行瞬间的自然日。

这避免 23:50 的提醒在次日 00:00 命中时被错误归到次日，也避免只用分钟绝对差导致 23:50 与 00:10 无法跨午夜匹配。非法日期、提前天数或 `HH:mm` 返回 `invalid_input`，不得发送。

### 防重键沿用字段但按计划提醒日期比较

`lastWechatExpiryReminderDate` 继续作为单日防重字段，但比较和写入值统一使用纯函数返回的 `reminderDate`。同一个计划窗口可能被相邻两次半小时调度命中，跨午夜时还可能落在两个自然日；使用计划日期可保证这些执行仍最多发送一次。

替代方案是继续写执行当天日期，但跨午夜相邻执行会出现两个不同日期，从而绕过防重。

### 测试纯逻辑并隔离外部依赖

将纯函数放入同目录 `expiryReminderDue.js` 并由 `index.js` 引用，使测试导入纯逻辑时不会触发云 SDK 初始化，也无需访问云数据库或微信 API。测试使用项目当前可用的 `node:test`，不新增测试依赖，覆盖周一、周三、周日，以及 08:30、09:00、21:30、23:50/00:10 和非法输入。

## Risks / Trade-offs

- [每 30 分钟扫描活动集合会增加云函数和数据库读取量] → 保留现有 1000 条上限，并在 P2 分页任务中进一步按候选日期缩小范围和分批扫描；部署前观察调用量。
- [相邻调度窗口可能同时命中同一提醒] → 继续使用 `lastWechatExpiryReminderDate` 防重；并发竞态由独立的原子 claim 任务处理，本次测试不宣称解决并发重复。
- [跨午夜时字段从执行日期改为计划提醒日期] → 字段格式仍为 `YYYY-MM-DD`，无需迁移；部署后旧值最多造成当前窗口一次跳过或重试，不影响后续日期。
- [服务器时区可能不同] → 纯函数只使用明确的东八区日期和时刻计算，不依赖 `Date#getHours()`；跨三个提醒云函数的公共实现仍留给后续统一时区任务。

## Migration Plan

1. 先部署包含纯函数、扫描判断、统计和测试的云函数代码。
2. 在测试环境以固定 `now` 样例验证日期、普通时间和跨午夜窗口，再执行云函数测试。
3. 更新 `config.json` 为每 30 分钟触发并重新部署触发器配置。
4. 观察首日的 sent、failed、date_mismatch、time_mismatch、duplicate 统计，确认调用量与候选分布。
5. 如需回滚，先恢复每周触发器配置，再回滚云函数代码；本变更无数据结构迁移。
