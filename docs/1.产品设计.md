## 一、产品定位

### 1.1 产品名称

**愈历** · 开药提醒

### 1.2 产品定位

一款面向**长期治疗患者及其家属**的微信小程序，聚焦"开药提醒"这一高价值核心场景，并逐步扩展到复诊、化验、影像等长期治疗随访提醒。

用户可以记录药物信息、最近一次开药时间、预计用药周期和提醒时间，在接近需要重新开药时收到微信提醒，**避免断药**。

当前小程序已从单一开药提醒扩展为「开药 + 药箱 + 检查/复诊提醒」的统一风险待办工具。产品叙事仍以「不要断药」为核心；检查/复诊提醒不再作为独立底部 Tab，而是并入「提醒」Tab 的统一提醒中心，作为长期治疗任务的一类提醒事项。

### 1.3 核心价值主张

```
不要断药
```

- **减少断药风险**：自动计算下次开药时间，提前推送提醒
- **降低记忆负担**：不再手动翻聊天记录或病历本
- **多药并行管理**：支持多种长期药物独立周期管理
- **复诊检查兜底**：将复诊、化验、影像等事项纳入同一个首页风险中心
- **家庭协作友好**：子女可代管父母长期用药，基于微信生态使用门槛低

## 二、目标用户

### 2.1 一线用户：年轻长期治疗患者（20–45 岁）

典型场景：

- 肺癌靶向药（如洛拉替尼）长期服用
- 乳腺癌、甲状腺癌术后维持用药
- 慢病长期处方（高血压、糖尿病、甲状腺功能异常）
- 精神类药物长期治疗

用户特点：数字化能力强、风险敏感、长期用药、主动管理意愿强。

### 2.2 二线用户：患者家属

典型场景：

- 子女帮父母管理长期用药
- 需要接收提醒、追踪开药周期
- 代为操作记录更新

### 2.3 通用慢病患者

- 高血压、糖尿病、甲状腺疾病等需定期复诊开药的用户
- 同时服用多种药物、各周期不同的用户

## 三、产品目标与阶段规划

### 3.1 当前阶段目标

验证以下核心假设：

1. 用户是否愿意长期记录和维护药物数据
2. 微信提醒是否有效触达并促使用户行动
3. 基于"开药周期"的提醒模型能否满足主要使用场景
4. 药箱资料和开药提醒合并到同一药品实体后，是否能降低维护成本
5. 复诊/检查提醒并入首页风险中心后，是否会增强长期治疗任务管理价值

## 五、核心功能设计

### 5.1 药物提醒管理

#### 字段设计

| 字段                      | 类型         | 必填 | 说明                                                    |
| ------------------------- | ------------ | ---- | ------------------------------------------------------- |
| `name`                    | string       | 是   | 药品名称，兼容旧字段 `medicineName`                     |
| `spec`                    | string       | 否   | 规格，如 20mg、1 盒 30 片，兼容旧字段 `medicineSpec`    |
| `reminderEnabled`         | boolean      | 是   | 是否启用开药提醒，药箱新增默认 false，首页新增默认 true |
| `currentPrescriptionDate` | YYYY-MM-DD   | 条件 | 最近一次开药日期，开启提醒时必填，默认今日              |
| `intervalDays`            | number（天） | 条件 | 开药间隔，快捷选项：3/7/14/28/30/45/60/90 天            |
| `remindAdvanceDays`       | number（天） | 条件 | 提前提醒天数，快捷选项：1/3/7/14/30 天，默认 7 天       |
| `remindTime`              | HH:mm        | 条件 | 提醒时刻，默认 09:00                                    |
| `status`                  | enum         | —    | 系统维护：`active` / `paused` / `deleted`               |
| `note`                    | string       | 否   | 备注，可填医院、用途、注意事项                          |
| `prescriptionHistory`     | string[]     | —    | 历史开药日期，最多保留 5 条                             |

#### 派生计算字段（不持久化，实时计算）

| 字段                   | 计算公式                                   | 说明                   |
| ---------------------- | ------------------------------------------ | ---------------------- |
| `nextPrescriptionDate` | `currentPrescriptionDate + intervalDays`   | 预计下次开药日期       |
| `nextRemindDate`       | `nextPrescriptionDate - remindAdvanceDays` | 提醒触发日期           |
| `daysLeft`             | `nextPrescriptionDate - today`             | 负数表示预计开药日已过 |
| `level`                | 见下表                                     | 紧急等级，驱动 UI 颜色 |
| `progress`             | `已过天数 / intervalDays × 100`            | 周期进度百分比         |

#### 紧急等级判定

| level     | 条件                             | 颜色 |
| --------- | -------------------------------- | ---- |
| `danger`  | `daysLeft ≤ 0`（逾期或今日到期） | 红色 |
| `warning` | `0 < daysLeft ≤ 7`               | 橙色 |
| `good`    | `daysLeft > 7`                   | 绿色 |
| `paused`  | `status === "paused"`            | 灰色 |

#### 排序规则

```
danger → warning → good → paused
同级按 nextPrescriptionDate 升序
```

### 5.2 提醒通知

#### 通知方案

| 渠道         | 策略     | 说明                                                 |
| ------------ | -------- | ---------------------------------------------------- |
| 微信订阅消息 | 主渠道   | 用户每次"已开药"或新增提醒时授权，云函数定时触发推送 |
| 小程序内首页 | 兜底展示 | 进入小程序后可见所有逾期和即将到期任务               |

#### 触发规则

1. 云函数 `reminder` 定时扫描需提醒数据
2. 当前实现：当 `today === nextRemindDate` 且当前时间命中 `remindTime` 时发送微信订阅消息
3. 用户点击消息进入详情页 → 执行"已开药"操作 → 自动进入下一周期
4. 待补齐：若用户未处理，逾期后次日再次提醒一次，最多补推一次

#### 提醒文案示例

```
标题：开药提醒

正文示例1：
您的「洛拉替尼」预计将在 7 天后需要重新开药，请提前安排复诊。

正文示例2：
「二甲双胍」今日需要处理开药事项，请避免断药。
```

### 5.8 药箱模块

#### 5.8.1 架构决策：统一 Medicine 实体

> **问题**：若将「药箱」与「提醒」设计为两张独立表，用户必须先在药箱新增药品，才能创建提醒——交互上存在强制前置步骤，摩擦明显。
>
> **解决方案**：合并为单一 `Medicine` 实体，在一张表（现有 `medicines` 集合）中同时承载药品信息与开药提醒配置。提醒功能通过 `reminderEnabled` 开关选择性启用，用户无需在两个入口间来回切换。

```
新增药品（唯一入口）
├── 基础信息：名称（必填）、规格、剂型、过期时间
├── 服药信息（选填）：每次用量、每日次数、服用时机（饭前、饭后、随餐、空腹、固定时间、按医嘱）
└── 开药提醒（开关，默认关闭）
    └── （开启后）最近一盒时间、下一盒时间、开药间隔、提前提醒天数、提醒时刻（这部分以现有功能为准）
```

**优势：**

- 零前置步骤：直接新增药品，按需开启提醒
- 单一数据源：药品信息与提醒配置同步更新，无外键对齐问题
- 复用现有集合：`medicines` 集合无需迁移，存量数据兼容

#### 5.8.3 药箱信息边界

药箱页定位为"药品资料管理"，只展示药品基础信息和服药信息，不展示开药倒计时、剩余量估算或库存风险。

**设计原则：**

- 若用户没有记录每次开药数量，则不展示推算库存，避免给出无依据的剩余量。
- 开药到期天数、逾期风险和已开药闭环统一放在首页风险中心、提醒列表和提醒详情中。
- 药箱卡片只承担资料检索与编辑入口，展示提醒是否已启用，但不重复提醒列表的风险文案。

## 七、关键业务流程

### 7.1 首次使用

```
进入小程序 → 微信授权登录 → 授权订阅消息
→ 点击「新增药品」→ 填写名称（必填）
→ 按需填写服药信息（选填）
→ 按需开启「开药提醒」开关（选填）→ 填写开药间隔等
→ 保存 → 系统生成提醒任务（若已开启）
```

### 7.2 到期提醒

```
云函数定时扫描
→ 查询 reminderEnabled=true && nextRemindDate=today 的 active 药品
→ 当前时间命中 remindTime
→ 发送微信订阅消息
→ 用户点击消息进入详情
→ 执行「已开药」→ 自动进入下一周期
```

待补齐目标：逾期未处理时，云函数应允许补推一次，避免用户错过提醒日后完全收不到订阅消息。

### 7.3 已开药闭环

```
点击「已开药」→ 确认本次开药日期（默认今天）
→ 更新 currentPrescriptionDate
→ 计算新的 nextPrescriptionDate / nextRemindDate
→ 写入 prescriptionHistory
→ 页面即时展示新的下次提醒日期和提醒状态
```

当前实现注意：部分入口未显式选择日期时会使用预计下次开药日期作为本次记录日期，后续应统一为"默认今天，可手动修改"。

### 7.4 药品过期提醒

```
云函数定时扫描
→ 计算 targetExpiryDate = today + ENV_EXPIRY_ADVANCE_DAYS
→ 查询 expiryDate=targetExpiryDate 的 active 药品
→ 当前时间命中药品提醒时间 / 过期提醒时间
→ 发送药品过期订阅消息
→ 写入 lastWechatExpiryReminderDate，避免当天重复发送
```

### 7.5 检查 / 复诊提醒

```
统一提醒中心 → 新增提醒 → 选择检查提醒 → 填写类型、检查日期、提前天数、提醒时间
→ 首页统一风险中心按紧急程度展示
→ 云函数命中 remindDate 后发送订阅消息
→ 用户完成检查
→ 可选择结束该事项，或重新安排下一次检查日期
```

### 8.1 medicines（统一药品主表，V1.1 重构）

> 原 `Reminder` 接口合并升级为 `Medicine`，集合名保持 `medicines` 不变。

```typescript
/** 剂型 */
type MedicineForm =
  | 'tablet'
  | 'capsule'
  | 'liquid'
  | 'injection'
  | 'external'
  | 'patch'
  | 'drops'
  | 'other';

/** 用量单位 */
type DosageUnit = '片' | '粒' | 'ml' | '支' | '贴' | '滴';

/** 服用时机 */
type MedicineSchedule =
  | '饭前'
  | '饭后'
  | '随餐'
  | '空腹'
  | '睡前'
  | '固定时间'
  | '按医嘱';

/** 药品状态（兼容原 ReminderStatus） */
type MedicineStatus = 'active' | 'paused' | 'deleted';

interface Medicine {
  id: string; // 主键

  // ── 基础信息 ──────────────────────────────────────────────────────────
  name: string; // 药品名称（必填，原 medicineName）
  spec: string; // 规格描述，如 "20mg/片"（原 medicineSpec）
  form: MedicineForm; // 剂型，默认 "tablet"（新增）
  expiryDate: string; // 过期时间 YYYY-MM-DD，可为空（新增）
  note: string; // 备注

  // ── 服药信息（选填，用于药箱资料展示）────────────────────────────────
  dosagePerUse: number; // 每次用量数，默认 1（新增）
  dosageUnit: DosageUnit; // 用量单位，默认 "片"（新增）
  timesPerDay: number; // 每日服用次数，默认 1（新增）
  scheduleTiming: MedicineSchedule; // 服用时机（新增）
  scheduleTime: string; // 固定时间时的具体时间 HH:mm，可为空（新增）

  // ── 开药提醒（reminderEnabled=true 时生效）───────────────────────────
  reminderEnabled: boolean; // 是否启用开药提醒，默认 false（新增）
  currentPrescriptionDate: string; // 最近开药日期 YYYY-MM-DD（原字段）
  intervalDays: number; // 开药间隔（天）（原字段）
  remindAdvanceDays: number; // 提前提醒天数（原字段）
  remindTime: string; // 提醒时刻 HH:mm（原字段）
  status: MedicineStatus; // 系统维护（原字段）
  prescriptionHistory: string[]; // 历史开药日期，最近 5 条（原字段）
  lastWechatReminderDate: string; // 最近一次成功推送日期（原字段）
  lastWechatReminderAt: string; // 最近一次成功推送时间 ISO（原字段）

  // ── 元数据 ──────────────────────────────────────────────────────────
  createdAt: string;
  updatedAt: string;
}

/** 派生计算数据（不持久化，实时计算） */
interface DerivedMedicine extends Medicine {
  // 提醒派生（原 DerivedReminder 字段）
  nextPrescriptionDate: string; // 预计下次开药日期
  nextRemindDate: string; // 提醒触发日期
  daysLeft: number; // 距今天数（负数=逾期，仅 reminderEnabled 时有意义）
  level: ReminderLevel; // 紧急等级
  levelLabel: string;
  progress: number; // 周期进度 0-100
  scheduleLabel: string; // 服用时机文案，如 "固定时间 20:00"
}
```

**存量数据迁移：** 为现有记录补填 `reminderEnabled=true`、`dosagePerUse=1`、`timesPerDay=1`、`expiryDate=""`、`scheduleTime=""`，业务逻辑完全兼容。

### 9.3 云函数设计

#### `auth`

- 微信登录（code2session）
- 用户信息初始化 / 更新

#### `reminder`

- 定时任务（`0 */30 * * * * *` 每30分钟触发）
- 当前实现扫描 `reminderEnabled=true && status=active`，逐条计算 `nextRemindDate`，命中当天和提醒时间后发送
- 调用微信订阅消息 API 发送提醒
- 更新 `lastWechatReminderDate`，消费用户订阅资格

#### `expiryReminder`

- 扫描 `expiryDate = today + ENV_EXPIRY_ADVANCE_DAYS` 的药品
- 命中时间后发送药品过期订阅消息
- 更新 `lastWechatExpiryReminderDate`

#### `checkupReminder`

- 扫描 `status=active` 的检查/复诊提醒
- 逐条计算 `targetDate - remindAdvanceDays`
- 命中当天和提醒时间后发送检查提醒订阅消息
- 更新 `lastWechatReminderDate`，消费用户订阅资格

## 十、状态设计

### 10.1 药品状态（`status`）

| 值        | 含义                                        |
| --------- | ------------------------------------------- |
| `active`  | 启用中，若 reminderEnabled=true 则正常推送  |
| `paused`  | 用户主动暂停，停止推送，仍展示在药箱/列表中 |
| `deleted` | 逻辑删除，不参与任何查询                    |

### 10.2 紧急等级（`level`，派生，仅 reminderEnabled=true 时有意义）

| 值        | 含义                             | UI 颜色 |
| --------- | -------------------------------- | ------- |
| `danger`  | 逾期或今日到期（`daysLeft ≤ 0`） | 红色    |
| `warning` | 7 天内到期（`0 < daysLeft ≤ 7`） | 橙色    |
| `good`    | 7 天以上（`daysLeft > 7`）       | 绿色    |
| `paused`  | 已暂停                           | 灰色    |

### 10.3 药箱提醒状态（`reminderEnabled`）

| 值      | 含义                                             | UI 展示           |
| ------- | ------------------------------------------------ | ----------------- |
| `true`  | 药品已启用开药提醒，进入首页风险中心和提醒列表   | `提醒已启用` 标签 |
| `false` | 药品仅作为药箱资料保存，不参与开药提醒和风险排序 | `未启用提醒` 标签 |

## 十一、边界与异常场景

| 场景                               | 处理策略                                              |
| ---------------------------------- | ----------------------------------------------------- |
| 用户未授权订阅消息                 | 小程序内首页仍展示待处理提醒；我的页引导授权          |
| 用户修改开药日期                   | 实时重算 `nextPrescriptionDate` / `nextRemindDate`    |
| 用户提前开药                       | 以最新输入的 `currentPrescriptionDate` 为准重新计算   |
| 漏处理逾期提醒                     | 待补齐：逾期后次日再次提醒一次（最多 1 次）           |
| 药物停用                           | 立即设置 `status = paused` 或 `deleted`，停止推送     |
| 多个药物同天提醒                   | 首页聚合展示，订阅消息分条发送                        |
| 间隔天数过短（< 1）或过长（> 365） | 前端表单校验，给出提示                                |
| 云函数推送失败                     | 当前记录云函数日志；后续可补充 `reminder_logs` 持久化 |
| 检查提醒已完成                     | 状态变为 `done`；可重新安排下一次检查日期             |
| 检查提醒与药品关联                 | 可关联药品用于上下文展示，不影响药品本身开药周期      |

## 十二、交互与体验原则

1. **输入尽量少**：优先选择器和快捷选项，减少手动键盘输入
2. **风险优先**：首页展示最紧急任务，而非功能入口
3. **重要操作直达**：首页卡片直接提供「已开药」按钮，无需进入详情
4. **老年友好**：字号、按钮、颜色对比度符合可读性要求
5. **即时反馈**：「已开药」后立即展示新的下次提醒日期
6. **快捷选项**：间隔 7/14/28/30/45/60/90 天；提前 1/3/7/14/30 天

## 十四、验收标准（当前阶段）

1. 用户可在 1 分钟内完成首个提醒创建
2. 系统正确计算下次开药日期和提醒触发日期
3. 用户点击「已开药」后，系统自动进入下一轮周期并即时展示新日期
4. 首页可正确按紧急程度排序展示开药提醒和检查提醒
5. 已授权订阅消息的用户，在提醒日期和提醒时间附近可收到微信提醒
6. 提醒数据跨小程序重启后可正确恢复（云数据库持久化）
7. 药箱可保存无提醒药品，并可随时开启开药提醒
8. 检查/复诊提醒可完成闭环，并可重新安排下一次检查日期
9. 我的页可完成订阅授权、默认提醒时间和默认提前天数设置
10. 通知历史收件箱和逾期二次提醒完成后，当前阶段才算完全收敛
